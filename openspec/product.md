# GlitchFlow - Product

## 目的

GlitchFlowは、処理の流れ(Flow)とデータの状態(State)を同じ時間軸で可視化するVSCode拡張機能である。
設計者、実装者、テスト担当者の認識のずれを減らし、設計の考慮漏れ(Glitch)の発見を支援する。
既存のDB設計書やAPI設計書を置き換えるものではない。
定義済みのデータが各処理の時点でどうなっているべきかを明示する。

## 設計上の優先事項

- `.glf` の記述を表示内容の正とし、描画側で処理、状態、差分を推測して補わない。
- DSLの記述順は時間軸の順序を表し、インデントは複合フラグメントやStateの階層を表す。
- 活性区間は明示的な `Object+` と `Object-` で制御し、インデントやメッセージの終了から自動終了させない。
- 応答メッセージを省略しても、明示された活性終了位置は正しく反映する。
- 分岐前の活性区間は、各分岐内の明示的な終了まで継続して表現する。
- 状態とSQLは設計意図を伝える表示情報であり、実行や状態遷移の推論は行わない。
- 読みやすさと正確な時間軸を優先し、内容を省略するよりスクロールによって全情報を確認できることを優先する。

## 利用者とユースケース

- 設計者は、基本設計、詳細設計で処理順序と期待状態を記述する。
- レビュアーは、要求、応答、DB、ファイルの整合性を一つの図で確認する。
- 実装者は、処理後の具体的な期待状態を確認する。
- テスト担当者は、結合試験の期待結果とデータエビデンスの確認に利用する。

## 対象機能

### DSLと編集

- 拡張子 `.glf` のテキストファイルを入力とする。
- VSCodeの通常のテキストエディタで編集する。
- 別のWebviewパネルにプレビューを表示し、編集内容に追従して更新する。
- 構文エラーや活性区間の不整合をVSCode上に表示する。
- DSLのインデントは分岐などの構造を表す。
- ファイル先頭の最初の非空行に、`title: "タイトル"` を任意で記述できる。
- `title` は1ファイルにつき1回だけ指定でき、空文字列は許可しない。
- 指定されたタイトルはプレビューの見出しに表示する。
- タイトルが未指定の場合は、`.glf` のファイル名をプレビューの見出しに表示する。
- タイトルは図のオブジェクトやライフラインを追加せず、状態やレイアウトにも影響しない。

### DSLエディタの配色

- `.glf` 専用の構文ハイライトを提供する。
- 標準では、VSCodeで選択中のカラーテーマに従ってキーワード、文字列、記号などを色分けする。
- 任意の設定 `glitchflow.syntaxHighlighting` を `glitchflow` に変更すると、GlitchFlow専用パレットで色分けする。
- 既定値は `theme` とし、選択肢は `theme` と `glitchflow` の2種類とする。
- 配色の切り替えは `.glf` の編集表示だけに適用し、VSCode全体のテーマやほかのファイルに影響させない。
- DSLに色指定を埋め込まず、図面のObject種別や複合フラグメントの固定色と、エディタの配色を独立させる。
- `title`、`Object`、`schema`、`state`、`sql`、複合フラグメント、メッセージ記号、活性記号、差分記号、文字列を識別する。

### シーケンス図

- `Object` でライフラインを宣言し、`APP`、`API`、`DB`、`FILE`、`FEATURE`、`MODULE` の種別を指定する。
- `Global` は暗黙の外部起点とし、オブジェクト枠やライフラインを描かず、メッセージの始点に丸を表示する。
- オブジェクトの基本色はAPP `#74C9F8`、API `#B287FF`、DB `#47D78B`、FILE `#EDA357` とする。
- FEATUREは `#E79BBE`、MODULEは `#A5B3C4` とする。
種別はオブジェクトの表示分類であり、FSDのレイヤーやソースコードの配置先は意味しない。
- `->>` は同期、`->` は非同期、`-->` は応答を表す。
- 逆向きの `<--` なども方向に応じて扱う。
- 同期メッセージの先端は塗りつぶし、非同期と応答の先端は開いた形状にする。
- メッセージとGlobalの丸は白系で統一する。
- `FE+` と `FE-` のような記法で活性区間を明示する。
- 応答メッセージは省略可能であり、`FILE-` などの明示的な活性終了で区間を閉じる。
- `FE: 処理名` で処理を表し、`*処理名*` は太字で強調する。
- 複合フラグメントは `alt`、`opt`、`loop`、`par`、`break` を対象とする。
- 複合フラグメントは共通の赤系 `#DD6872` で表す。
- フラグメントの枠、ラベル、分岐線を前面に描き、内側の処理は隠さない。

### データ状態

- `schema ObjectID.table:` と `schema ObjectID.schema.table:` の両形式で、DBテーブルのカラム名と型を宣言する。
- `state` も `state ObjectID.table:` と `state ObjectID.schema.table:` の両形式を許可する。
- `ObjectID` は `type DB` のオブジェクトIDを表し、スキーマ名は省略可能とする。
- スキーマ名を省略しても補完やDB製品ごとの名前解決は行わず、記述された識別子をそのまま扱う。
- DBレコードの先頭は `+ [値, ...]` が追加、`- [値, ...]` が削除、`[値, ...]` が変更なしを表す。
- DBレコード内の `!値` はそのカラムの更新を表し、更新後の値だけを記述する。
- DBテーブルは全カラムを横並びで表示し、勝手に省略、分割しない。
- `state FILE:` は階層付きのファイルツリーを記述し、各ファイル、フォルダの `+` は追加、`-` は削除、無印は変更なしを表す。
- DB、FILEとも、追加と更新は赤文字、削除は赤文字と取り消し線、変更なしは通常の文字色で描画する。
- DBのカラム更新は `!` が付いたセルだけを赤文字にする。
- `+`、`-`、`!` はDSL上の指定記号であり、図面には表示しない。
- FILEの親子間で変更の指定を自動伝播せず、各要素の明示指定を使う。
- `sql ObjectID:` でSQL文を記述し、グレー系の矩形内にテキストとして表示する。
- 同じDBに対する `state` の直後に `sql` が続く場合、SQL枠をテーブルの下に配置する。
- StateはDSLに書かれた場所でのみ描画し、全ステップへ自動挿入しない。
- Stateはその時点の表示用状態と変更の注釈であり、DB操作やファイル操作を実行する命令ではない。
- 前後のStateを比較せず、レコードやFILEの変更の整合性、SQLとの整合性を検証しない。
- 構文の誤りや参照先の識別子の誤りは、引き続き診断対象とする。

### タイトル記述例

```text
title: "ログインフロー"

Object FE as "フロントエンド" type APP
```

`title` は先頭の最初の非空行に指定する。
この例ではプレビューの見出しを"ログインフロー"とし、未指定時はファイル名を表示する。

### State記述例

```text
Object DB as "PostgreSQL" type DB
Object FILE as "Storage" type FILE

schema DB.public.users:
    uid: int
    name: text
    status: text

state DB.public.users:
    - [1, "taro", "inactive"]
    [2, "jiro", "active"]
    [3, !"saburo", "active"]
    + [4, "shiro", "active"]

state FILE:
    users/
        1/
            - old.info
            user.info
            + new.info
```

上記のDBでは1行目が削除、2行目が変更なし、3行目の `name` が更新、4行目が追加を表す。
`DB.users` のようにスキーマ名を省いた記述も可能とする。
この例は描画仕様を示すものであり、変更が実際に成立するかは検証しない。

### 図面の操作

- スクロールと拡大、縮小ができる。
- 図のテキストを選択、コピーできる。
- 状態表示のサイズに応じて配置を自動調整する。
- メッセージ、活性区間、状態表示、複合フラグメントが不自然に重ならないようにする。

## ドメイン用語

| 用語 | 意味 |
| --- | --- |
| Title | `.glf` ファイルごとの任意の表示見出し |
| Object | シーケンスに登場する対象 |
| Lifeline | Objectの時間方向の軸 |
| Message | Object間の要求、通知、応答 |
| Activation | 明示的な `+` から `-` までの実行仕様 |
| Fragment | 条件分岐、繰り返し、並列などの複合フラグメント |
| Schema | DBテーブルの表示用カラム定義(スキーマ名は省略可能) |
| State | 指定された時点のDBまたはFILEの期待状態と明示的な変更情報 |
| SQL | 図中に表示するSQLテキスト(実行はしない) |
| Event | メッセージ、処理、状態、活性操作など、時間軸上の要素 |

## 開発範囲

初期の縦断的な実装では、`examples/login.glf` に登録するログイン例を題材に `alt` までの描画と編集連携を完成させる。
基準DSLは最初の実装変更で用意し、既存の外部資料を前提として実装を進めない。
その後、`opt`、`loop`、`par`、`break` を独立したOpenSpec変更として追加する。
これら5種類を複合フラグメントの目標機能とする。

## 対象外

- SQLの実行、実DBへの接続、Stateに記載した業務ファイルへの読み書きは行わない。
- `.glf` 自体の通常の編集とプレビュー用の読み取りは対象に含める。
- 実際の試験の実行やエビデンスの自動収集は行わない。
- 図面上のドラッグ操作によるDSL編集は初期対象外とする。
- Excelファイルの自動変換、AIによるDSL自動生成、クラウド同期は初期対象外とする。
- 自然言語やSQLから正しい期待Stateを推論する機能は実装しない。
- 前後のStateから差分を自動判定する機能や、変更操作の実行可否を検証する機能は実装しない。

## 成功条件

- 既存のExcelによる図面調整を、DSLの編集と自動描画に置き換えられる。
- `.glf` のタイトルとエディタ配色を、DSLおよびユーザー設定に従って表示できる。
- 処理と期待状態が同じ時間軸で読める。
- 実装、テストの認識違いを減らすための情報を、無理なく記述できる。
